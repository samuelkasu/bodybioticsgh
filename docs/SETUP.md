# Body Biotics GH — PWA setup and architecture reference

This is the reference for how the repo is put together and why. Every choice below is already implemented in the tree — file paths are given so you can read the real thing rather than a snippet.

Stack: Next.js 16 (App Router, Turbopack) · TypeScript strict · Tailwind v4 · Redux Toolkit + RTK Query · Serwist service worker · ASP.NET Core 10 + PostgreSQL · Jest + React Testing Library · Playwright · Docker Compose · GitHub Actions.

---

## 1. Quick start

```bash
node -v                        # 20.11+ (CI runs 22; see engines in frontend/package.json)
dotnet --version               # 10.0+
docker compose up -d postgres redis

# terminal 1 — API on :5080, migrates and seeds itself in Development
cd backend
dotnet run --project src/BodyBiotics.Api

# terminal 2 — PWA on :3000, proxies /api to the API
cd frontend
npm ci
cp .env.example .env.local
npm run dev
```

To exercise the PWA (service worker, install prompt, offline fallback):

```bash
npm run build && npm start    # build runs next build, then serwist build
```

The service worker is **not** generated in dev (`frontend/src/components/pwa/ServiceWorkerRegistrar.tsx` bails out when `NODE_ENV !== "production"`). This is deliberate: a stale worker in dev is the single most confusing class of PWA bug — you fix code, reload, and see the old app.

## 2. Repository layout

Two workspaces under one repository, so a change that spans the API and the UI is one commit and one pull request.

```
.github/workflows/ci.yml       frontend · backend · e2e · docker
docker-compose.yml             postgres + redis for local development
docs/SETUP.md                  this file

frontend/                      Next.js 16 PWA

  public/
    catalog/<slug>/            imported product photos as WebP
    icons/                     generated by npm run icons
    sw.js                      generated, gitignored
  scripts/
    generate-icons.ts          sharp-based icon pipeline
    import-catalog.ts          one-off WooCommerce mirror importer
  src/
    app/
      layout.tsx               document shell, providers, PWA pieces only
      not-found.tsx            outside (shop), so the 404 renders with no chrome
      (shop)/                  the storefront: header, footer, cart drawer, and
                               /, shop, product, category, brand, cart,
                               checkout, order, account, admin, about, contact
    components/
      commerce/                cards, grid, filters, cart, checkout, orders
      layout/                  header, nav, cart drawer, footer
      home/                    hero, selling points, testimonials
      ui/                      button, fields, skeleton, empty and error states
      pwa/                     install, update, offline, SW registration
    lib/
      api/                     baseApi (RTK Query) + http (wire contract types)
      auth/                    cookie names shared with the API
      env.ts                   zod-validated configuration
      features/<domain>/       slice + endpoints + types
      store/                   store, typed hooks, provider
    proxy.ts                   route protection (Next 16 renamed middleware → proxy)
    test/test-utils.tsx        renderWithProviders

backend/                       ASP.NET Core 10 API
  BodyBiotics.slnx
  seed/catalog.json            imported catalogue, read by DatabaseSeeder
  seed/import-report.md        import review artefact
  src/BodyBiotics.Api/         endpoints + application services, auth, OpenAPI
  src/BodyBiotics.Domain/      entities, business rules, repository interfaces
  src/BodyBiotics.Infrastructure/  EF Core, Npgsql, repositories, migrations
  tests/BodyBiotics.Tests/     xUnit (domain, services, validators)
```

Feature-first, not layer-first on the frontend: `frontend/src/lib/features/cart/` holds the slice, its selectors and its tests together. When cart logic changes you touch one folder, not four. The backend is layered instead (Domain / Infrastructure / Api), which is the idiomatic split in .NET and keeps EF Core out of the business rules. Endpoints are thin: they bind and delegate to an application service (`CatalogueService`, `CartService`, `CheckoutService`, `ContactService`), which works through repository interfaces declared in `BodyBiotics.Domain/Abstractions` and implemented over EF Core in `BodyBiotics.Infrastructure/Repositories`. That is what makes the service tests run against fakes with no database.

`frontend/public/sw.js` is a build output — gitignored, regenerated by `postinstall` and `build:sw`.

## 2.5 Where the catalogue came from

The storefront replaces a WordPress/Elementor/WooCommerce site. A static mirror of that site was imported once by `frontend/scripts/import-catalog.ts` (`npm run import:catalog -- <mirror-path>`), which writes three things:

- `backend/seed/catalog.json` — 340 products, 34 categories, 105 brands. Committed, and the only input the database seeder reads.
- `frontend/public/catalog/<slug>/{main,800,400}.webp` — 17MB of WebP, down from ~90MB of source JPEG.
- `backend/seed/import-report.md` — the review artefact: what matched, what did not, and why.

Facts worth knowing about the source data:

- Product data came from each page’s `application/ld+json`, which is far more reliable than scraping Elementor markup. Category came from breadcrumb position 3.
- **Brand membership was not recoverable.** Every scraped brand archive rendered the same default 24-product loop, so brands are matched from the product title (longest name first) plus an override map in the script. 313 of 340 products have a brand; the rest are genuinely unbranded (bath brushes, generic soaps) and are left without one rather than guessed.
- No sale prices and no product variations existed anywhere in the source, which is why neither appears in the schema.
- One product had no price. It is imported with `active: false` rather than listed at zero.
- Stock was only ever in/out on the old site, so in-stock products are seeded with a nominal level for checkout to decrement.

To re-run after fixing a brand: edit `BRAND_OVERRIDES`, re-run the script, review the report, then re-seed. Seeding is idempotent and never resets live `Stock`.

## 3. Frontend

### 3.1 Framework and build

Next.js 16 App Router, `frontend/src/` directory, `@/*` path alias. Turbopack is the default builder in 16.

**Gotcha that shapes the whole PWA setup:** `@serwist/next`'s webpack plugin forces the legacy webpack builder and Next 16 errors out (`This build is using Turbopack, with a webpack config`). So the service worker is built as a **post-build CLI step** instead:

```jsonc
// package.json
"build": "next build && npm run build:sw",
"build:sw": "serwist build serwist.config.mts",
```

`frontend/serwist.config.mts` must be `.mts`, not `.ts` — the Serwist CLI imports the config as an ES module, and a `.ts` file in a non-`type: module` package is loaded as CommonJS, where its top-level `await` fails.

Consequence: nothing injects a registration snippet for you, so registration is explicit in `frontend/src/components/pwa/ServiceWorkerRegistrar.tsx`.

### 3.2 Service worker and caching

Source: `frontend/src/app/sw.ts`. Strategies, in priority order:

| Route                                                      | Strategy                                                | Why                                                                                                                                                                            |
| ---------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Same-origin images                                         | `CacheFirst`, 120 entries, 30 days, `purgeOnQuotaError` | Product photos dominate page weight and are immutable per URL. The entry cap protects the device quota — iOS evicts the _whole_ origin when it runs out, not the oldest entry. |
| `/api/auth/*`, `/api/cart*`, `/api/checkout*`, any non-GET | `NetworkOnly`                                           | A replayed cart or session response shows a customer stale or someone else's state. Never cache money or identity.                                                             |
| `GET /api/products*`                                       | `NetworkFirst`, 3s timeout, 1 day                       | Fresh when online, last-known catalogue when the tunnel drops mid-scroll. The timeout is what stops a dying connection from hanging the grid.                                  |
| Fonts                                                      | `CacheFirst`, 1 year                                    | They never change; a revalidation round-trip per launch is wasted latency.                                                                                                     |
| CSS/JS                                                     | `StaleWhileRevalidate`                                  | Instant paint, update in background.                                                                                                                                           |
| Navigations                                                | Serwist defaults + `/offline` fallback                  | Installed apps have no browser error page to fall back on.                                                                                                                     |

Precache scope is deliberately narrow (`frontend/serwist.config.mts`): `.next/static` JS/CSS/fonts plus icons. The default glob sweeps all of `frontend/public/`, which here is ~17MB of photography and a 17MB video — downloading that on first visit over mobile data is indefensible. Current precache: 30 URLs / 1.33MB, mostly framework chunks.

`skipWaiting: true` + `clientsClaim: true`: for a storefront, a half-updated app (old shell, new API) is riskier than a forced refresh — prices and stock must agree. `frontend/src/components/pwa/UpdatePrompt.tsx` surfaces a waiting worker as a "new version available" bar, because an installed PWA never reloads on its own and a customer can otherwise sit on a weeks-old build.

`frontend/next.config.ts` sends `Cache-Control: no-cache, no-store, must-revalidate` for `/sw.js`. If a CDN pins the worker, the app freezes on that build for everyone — this is the most expensive PWA mistake to recover from.

### 3.3 Manifest and installability

`frontend/src/app/manifest.ts` → served at `/manifest.webmanifest`. Android/Chrome needs `name`, `short_name`, `start_url`, `display: standalone`, and 192px + 512px icons before it will offer installation. A `purpose: "maskable"` icon with ~20% padding stops the logo being cropped by adaptive launcher shapes.

`start_url: "/?source=pwa"` marks installed traffic in analytics without changing routing.

Icons are generated from one source file: `npm run icons -- public/assets/LOGO.png` (`frontend/scripts/generate-icons.ts`, sharp). Kept out of the build path on purpose — icons change once a year and sharp in CI is a portability liability.

### 3.4 Mobile-first and viewport

`frontend/src/app/layout.tsx` exports `viewport`:

- `width=device-width, initial-scale=1`
- `maximumScale: 5` — **do not** set `user-scalable=no`; it is an accessibility failure and Lighthouse flags it.
- `viewportFit: "cover"` + `env(safe-area-inset-*)` padding in components — without both, content sits under the iPhone notch and home indicator when installed.
- `themeColor` with light/dark variants.

Component conventions: Tailwind mobile-first breakpoints (base styles are the phone layout, `sm:`/`lg:` widen it), minimum 44px tap targets (`min-h-11`), `next/image` with explicit `sizes` so phones get phone-sized files, `priority` only on the first row, and `display: "swap"` on fonts so text is visible during load on 3G.

### 3.5 State management

Two kinds of state, deliberately separated:

- **Server data** — RTK Query (`frontend/src/lib/api/baseApi.ts`). One API instance; new endpoints are _injected_ (`injectEndpoints`) rather than creating a second api. Tag-based invalidation (`Product`, `Cart`, `Order`, `Session`).
- **Client state** — slices under `frontend/src/lib/features/*`: `cartSlice` (optimistic cart mirror), `networkSlice` (online/offline, connection quality, waiting SW update).

`makeStore()` creates a fresh store per call — the server never shares state between requests, and every test gets isolation for free. `StoreProvider` lazy-inits one store per tab.

Low-bandwidth handling:

- `keepUnusedDataFor: 120` and `refetchOnReconnect: true` on the API — a storefront on mobile data should not refetch on every tab focus.
- `selectIsLowBandwidth` (from the Network Information API's `effectiveType` and `saveData`) gates heavy work. `ProductGrid` requests 6 items instead of 12 on a slow or metered link. Note Safari implements none of this, so the selector returns `false` on iOS — never _degrade_ based on it, only _reduce_.
- The response envelope is unwrapped centrally in `envelopeBaseQuery`, so the `{ data }` wrapper never reaches components.

## 4. Backend

ASP.NET Core 10 Minimal APIs, layered Domain / Infrastructure / Api, EF Core 10 on PostgreSQL. The frontend serves no API routes at all — there is one owner of sessions and one owner of the database.

### 4.1 Why the browser never calls the API directly

`frontend/next.config.ts` rewrites `/api/:path*` to `API_ORIGIN` (default `http://localhost:5080`). The browser only ever sees the Next origin.

That is not cosmetic. `bb_session` has to be a **first-party** cookie: Safari blocks third-party cookies outright, and an installed PWA on iOS would silently lose its session mid-checkout. The proxy also removes every CORS preflight — one fewer round-trip per mutation on mobile data.

The API reads `X-Forwarded-For` and `X-Forwarded-Proto` (`UseForwardedHeaders`), so rate limiting partitions by the real client IP rather than the proxy's — but only from proxies named in `App:TrustedProxies` (single addresses, or CIDR ranges such as `172.16.0.0/12` for a Docker bridge network). This must be set in every deployed environment. Leave it empty and only loopback is trusted, so a proxy in another container is ignored, every customer lands in one rate-limit bucket, and a handful of simultaneous checkouts locks the shop; the API logs a warning at startup when that is the case. Never "fix" it by trusting everything — an unrestricted list lets anyone spoof `X-Forwarded-For` and walk past the login limiter.

### 4.2 API architecture

Minimal APIs grouped by feature (`Features/Products`, `Features/Auth`), mapped under one `/api` group in `Program.cs`.

Every response is the same envelope — `{ "data": … }` or `{ "error": { code, message, details? } }` — produced by `ApiResults` and enforced by `ApiExceptionHandler`:

- `ApiException` → its mapped status.
- FluentValidation `ValidationException` → 400 with field-keyed details.
- Anything else → 500, logged, **as JSON**. An HTML error page is poison for a PWA: the client parses it as JSON and the failure looks like a network fault.

This is deliberately not `ProblemDetails`. The contract predates the .NET API, the TypeScript client unwraps it in one place (`baseApi`), and responses already cached by installed service workers have this shape.

Nulls are serialised, not omitted (`JsonIgnoreCondition.Never`): `{ "user": null }` means signed out, whereas `{}` reaches TypeScript as `undefined` and reads as "unknown".

Cache headers are explicit per endpoint (`CacheHeaders`): catalogue reads are `public, s-maxage=60, stale-while-revalidate=300`; anything user-specific is `private, no-store`.

Staff endpoints live under `/api/admin` (orders queue, order status transitions, catalogue price/stock/visibility) behind an `admin` authorization policy applied to the whole group, so a route added later is protected by default. Cancelling an order there returns its reserved stock. The admin product list includes inactive products, which the storefront list hides — otherwise deactivating one would be a one-way door — and carries stock levels on its own DTO, because the public `ProductDto` deliberately exposes only `inStock`.

Endpoints: `GET /api/health`; catalogue `GET /api/products` (page, perPage≤48, search, category, brand, minPrice, maxPrice, sort), `GET /api/products/{slug}`, `GET /api/categories`, `GET /api/brands` and their `/{slug}` archives; cart `GET/POST/PATCH/DELETE /api/cart`; `POST /api/checkout`, `GET /api/orders`, `GET /api/orders/{reference}`; `POST /api/contact`; auth `POST /api/auth/{register,login,logout,forgot-password,reset-password}`, `GET /api/auth/session`. OpenAPI plus a Scalar UI are served in Development at `/openapi/v1.json` and `/scalar`.

### 4.3 Authentication and sessions

Cookie authentication (`Microsoft.AspNetCore.Authentication.Cookies`), not bearer tokens in `localStorage` — XSS reads `localStorage`, and iOS clears it aggressively.

- `bb_session`: `HttpOnly`, `Secure` outside development, `SameSite=Lax`, 30-day sliding expiry.
- **Lax, not Strict:** Paystack and Hubtel redirect back into the app after payment; a Strict cookie is not sent on that navigation and the customer lands signed out.
- The cookie carries a `sid` claim pointing at a `Session` row. `SessionValidator` re-checks that row on every authenticated request, so "sign out this device" takes effect immediately instead of in 30 days. It also refreshes `LastSeenAt`, throttled to once per 15 minutes so an active shopper does not cause a write per request.
- 401 and 403 return the envelope; the cookie handler's default redirect-to-login is overridden, because an API that answers a fetch with an HTML login page breaks the client.
- Passwords: ASP.NET Core's `PasswordHasher<T>` (PBKDF2, versioned format). It reports `SuccessRehashNeeded`, so logins transparently upgrade old hashes. A malformed stored hash returns "failed", never throws — that was a real bug the unit tests caught.
- Unknown emails still burn a hash (`TimingEqualiserPassword`) so response time does not enumerate accounts.
- `/api/auth/login` and `/api/auth/register` are rate limited to 10 requests per minute per IP, rejected with `RATE_LIMITED` in the envelope.

Long sessions are a product decision: an installed PWA is treated like an app. Security comes from revocation, not short expiry.

### 4.4 Database

PostgreSQL 16, EF Core 10 with Npgsql, snake_case columns (`UseSnakeCaseNamingConvention`) so the schema reads normally from `psql`.

- **Money is `int` in minor units** (pesewas), never `decimal` or `double`. `Money` in the Domain project is the only place that converts, and check constraints (`ck_product_price_minor_non_negative`, `ck_product_stock_non_negative`) stop a negative price reaching the table whatever the application does.
- `OrderItem.UnitPriceMinor` copies the price at purchase time — prices change, receipts must not. The delivery details (name, phone, address, city, notes) are copied onto the order for the same reason: an account's address changes, and a delivery already made must still show where it went.
- `Order.RequestId` is uniquely indexed: that index, not application logic, is what makes a checkout retried over a flaky connection idempotent.
- `Order.Status` has a private setter and `TryTransitionTo`. Payment webhooks arrive late, out of order and more than once; re-delivery of a transition already applied returns `true`, an illegal one returns `false`.
- `Cart` is keyed by user or anonymous cookie. The Redux cart is the optimistic mirror; this copy survives reinstalling the app, switching device, or iOS evicting the origin's storage.
- Enums are stored as text, so reordering the C# enum cannot silently promote every customer to admin.
- `Identifier.New()` produces time-sortable ULID-style ids: index inserts stay at the right edge of the B-tree, and an order id does not leak how many orders exist.
- `Identifier.OrderReference()` is `BB-yyyyMMdd-` plus 40 bits from the cryptographic RNG in Crockford base32 (no I, L, O or U, so nothing is misheard over the phone). It was five digits, which collided against the unique index about one day in five at 200 orders a day and was short enough to guess. A guest order is readable only by the browser holding the `bb_orders` grant cookie issued at checkout (`OrderAccessGrant`) — never by reference alone.

Migrations live in `backend/src/BodyBiotics.Infrastructure/Persistence/Migrations` and are applied with `dotnet ef database update` locally, or by `App__MigrateOnStart=true` in development and CI. In production, run migrations as a separate step before the new image takes traffic — never `MigrateOnStart` against a live cluster where several instances start at once.

`DatabaseSeeder` is idempotent and refuses to reset `Stock`, which is live trading data.

### 4.45 Payments

Hubtel Online Checkout (`backend/src/BodyBiotics.Infrastructure/Payments`), bound from the `Hubtel` configuration section. The hosted checkout is used rather than the direct Receive Money prompt, so card details never reach this server.

Pay on delivery remains a first-class option: `Order.PaymentMethod` is `OnDelivery` or `Hubtel`, and `GET /api/payments/methods` tells the storefront which to offer. With no credentials set the gateway reports itself unconfigured, the online option disappears, and the shop trades exactly as it did before.

**The callback is not evidence.** Hubtel signs nothing, so `POST /api/payments/hubtel/callback/{secret}` treats the body as a nudge: it reads the client reference and then asks Hubtel's status endpoint directly, and only that answer settles an order. The secret in the path keeps the endpoint from being casually discovered — it is not the control. Two further guards: the paid amount is compared against the order total before it settles, and every path is idempotent, because callbacks are retried and the order page reconciles as well.

`/order/[reference]` polls every four seconds while a Hubtel order is pending and stops the moment it settles, which is what covers a callback that is late, lost or blocked by a firewall.

The provider is called **after** the checkout transaction commits. An HTTP round-trip while holding row locks on stock would let a slow gateway stall every other checkout. If the provider cannot be reached, the order is cancelled and its stock released immediately rather than left unpayable.

Both base URLs are configuration (`Hubtel:CheckoutBaseUrl`, `Hubtel:StatusBaseUrl`): Hubtel has moved these between hosts before, and that should be a config change rather than a redeploy. The status API may want a different credential pair from the checkout one — `Hubtel:StatusApiId` and `Hubtel:StatusApiKey` exist for that, and fall back to the checkout pair when unset.

### 4.46 Email

SMTP over MailKit (`backend/src/BodyBiotics.Infrastructure/Email`), bound from the `Email` section. SMTP rather than a provider-specific API on purpose: Resend, Brevo, Zoho, Mailgun and SendGrid all speak it, so changing provider is a configuration change. Port 465 is detected and switched to implicit TLS; anything else uses STARTTLS.

**Nothing sends on the request thread.** `EmailOutbox` is a bounded channel drained by `EmailDispatcher`, a `BackgroundService`, with three attempts and a widening backoff. The order is already committed when a message is queued — a provider having a bad minute must not turn a placed order into a 500 that the customer reads as "it did not go through". The queue is bounded, so a wedged provider cannot grow it until the process runs out of memory; a full queue drops and logs at Error.

`OrderNotifier` is the single place that decides which message a state change produces: confirmation on placement, a separate alert to `Email:ShopInbox` with `Reply-To` set to the customer, a receipt when Hubtel settles, a dispatch notice on Fulfilled, and a cancellation notice. Marking a **pay-on-delivery** order Paid deliberately sends nothing — that transition means the rider collected the cash at the door.

Templates (`Api/Features/Notifications/EmailTemplates.cs`) always build both an HTML and a plain-text body. The HTML is one table with inline styles, no stylesheet, no web font and no remote image, because Gmail strips `<style>` blocks and an image-blocked client should still show a complete receipt. Every interpolated value is HTML-escaped — names and delivery notes are free text that ends up inside markup.

With `Email:Host` or `Email:FromAddress` unset the sender reports itself unconfigured, logs the subject and recipient (never the body — a reset link in the application log is a live credential) and drops the message. Password reset refuses outright in that state rather than accepting a request it cannot fulfil.

`Email:SiteUrl` must be the real storefront origin. It builds every link in every message.

### 4.47 Password reset

`POST /api/auth/forgot-password` and `POST /api/auth/reset-password`, both on the login rate-limit policy. Only the SHA-256 of the token is stored (`password_reset_tokens`); the plaintext exists once, in the email, so a database dump does not yield working reset links. Tokens are single-use and expire in 60 minutes, and a second request invalidates the first.

Three things the implementation is deliberate about. An unknown address takes the same path and gets the same response as a known one, because the login path already refuses to leak which addresses have accounts and a reset form is the obvious place to reopen that. Expired, spent and never-existed all give one message, for the same reason. And every session is revoked in the same `SaveChanges` as the password change — the usual reason for a reset is that somebody else has the password.

On success the customer is signed in and redirected to `/account`. `/account/reset-password` is `noindex` and already inside the `robots.txt` `/account/` disallow.

### 4.5 Configuration

`AppOptions` is bound from the `App` section and validated with `ValidateOnStart()`, so a missing connection string fails the deploy rather than the first checkout. Override anything with environment variables using the double-underscore form: `App__ConnectionString`, `App__MigrateOnStart`, `App__CorsOrigins__0`.

Secrets locally: `dotnet user-secrets`, never `appsettings.json`. The API project carries a `UserSecretsId`, so `dotnet user-secrets set "Hubtel:ClientSecret" "…" --project src/BodyBiotics.Api` works from `backend/`. The same applies to `Email:Password` and the rest of the `Email` section. Values land in your user profile, outside the repository.

Package versions are pinned centrally in `backend/Directory.Packages.props`, and `backend/nuget.config` clears machine-level feeds. Without the first, the Npgsql provider and the EF Design package resolve different `EntityFrameworkCore.Relational` assemblies and the build fails with an error that reads like a compiler bug.

`Directory.Build.props` turns warnings into errors for the whole solution, so analyzer findings surface locally rather than in a pull request. `.editorconfig` exempts `**/Migrations/*.cs`, because generated EF code does not satisfy hand-written-code analyzers.

## 5. DevOps and tooling

### 5.1 Local environment

- Node 20.11+ (`engines`), CI on 22, and the .NET 10 SDK. Use nvm/Volta to pin Node.
- `docker compose up -d postgres redis` (or `npm run db:up` from `frontend/`). Postgres has a healthcheck because migrations run straight after and otherwise race first-boot initialisation on a cold volume.
- A second `postgres-test` service (profile `test`, port 5433, tmpfs) so an E2E run can be wiped without touching development data.
- `docker compose --profile full up` also builds and runs the API in a container. Day to day, run it with `dotnet run` instead — hot reload beats a rebuild per change.
- Two terminals: `cd backend && dotnet run --project src/BodyBiotics.Api` (port 5080) and `cd frontend && npm run dev` (port 3000).

### 5.2 Build and deployment

`frontend/next.config.ts`:

- `output: "standalone"` → minimal server bundle for the Docker image.
- `rewrites()` proxies `/api/*` to `API_ORIGIN`, which is what keeps the session cookie first-party.
- `images.formats: ["image/avif", "image/webp"]` and phone-first `deviceSizes`.
- Security headers: `nosniff`, `strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, a `Permissions-Policy` that denies camera/microphone and allows geolocation/payment only same-origin, `Strict-Transport-Security` (one year, `includeSubDomains`, no `preload`), and a `Content-Security-Policy` that is `'self'` throughout. `script-src`/`style-src` keep `'unsafe-inline'` for Next's hydration bootstrap and next/font; the alternative is a per-request nonce from `proxy.ts`, which makes every page dynamic. **Do not add `upgrade-insecure-requests`** — it rewrites the service worker's precache fetches to https, they fail on a plain-http origin, and the worker silently never installs. A payment provider will need its own `script-src`, `connect-src` and `frame-src` entries.

Two images. `frontend/Dockerfile` is three stages (deps → builder → runner) on `output: "standalone"`. `backend/Dockerfile` restores from the csproj files first so the layer caches, publishes Release, and runs on the ASP.NET runtime image as uid 1001. Both run as non-root and healthcheck `/api/health`.

Deploy order that avoids downtime: apply EF migrations → roll the API → roll the frontend. The new service worker then prompts installed clients to refresh.

### 5.3 Testing

Three layers, each earning its place:

**Backend unit (xUnit)** — `cd backend && dotnet test`. 157 tests over the order state machine, money conversion, cart totals, session expiry/revocation, id generation, validators, the password hasher, password-reset tokens, the emails each order transition produces, and the application services (catalogue filtering and sorting, cart add/update/merge, checkout pricing, stock reservation and idempotency, admin transitions, payment reconciliation). Services are tested against hand-written fakes in `tests/BodyBiotics.Tests/Fakes`, so the whole suite needs no database and runs in the fast CI job.

**Frontend unit (Jest + RTL)** — `cd frontend && npm test`. 111 tests over reducers, selectors, the error envelope, the network slice, the RTK Query parameter mapping, and the components that carry money or state: `ProductCard` (optimistic add and rollback), `Pagination` (window, boundaries, href building), `QuantityStepper` (clamping, empty input), and the checkout/contact/credential validators. Notes:

- `frontend/jest.environment.js` is a custom jsdom environment that injects Node's fetch family (`fetch`, `Request`, `Response`, `AbortController`, …). jsdom ships none of it, and mixing jsdom's `AbortSignal` with Node's `Request` throws a cross-realm error.
- A test needing real Node APIs rather than jsdom opts in with `/** @jest-environment node */`.
- `modulePathIgnorePatterns: ["<rootDir>/.next/"]`, or `.next/standalone/package.json` collides with the root one in jest-haste-map.
- `renderWithProviders` (`frontend/src/test/test-utils.tsx`) renders with a real store; pass your own to seed or assert on state.

Saved items live server-side for the same reason the cart does — see §6.3 on iOS eviction — and an offline checkout is held in IndexedDB keyed by its `requestId`, then replayed by `frontend/src/components/pwa/OfflineOrderQueue.tsx` on reconnect and on next app open. Replay reuses the key, so the API returns the original order rather than creating a second.

**E2E (Playwright)** — `npm run test:e2e`. Runs against a **production build** (`webServer` runs `npm run build && next start`), because the service worker does not exist in dev. Projects: `android-chrome` (Pixel 7), `ios-safari` (WebKit), `desktop-chrome`. Three specs: `pwa.spec.ts` (manifest fields, apple-touch-icon, `viewport-fit=cover`, `/sw.js` cache headers, offline fallback), `api.spec.ts` (envelope, pagination, sorting, category filtering, 400s, 404s, and a full add-to-cart → checkout → idempotent-retry run), and `storefront.spec.ts` (home, shop paging, search surviving a reload, product page, checkout and contact validation, and the `/account` redirect).

WebKit is a regression net, not an iPhone: no home-screen install, different storage eviction. Smoke-test a real device before release.

`frontend/e2e/pwa.spec.ts` runs without a backend at all. `frontend/e2e/api.spec.ts` needs Postgres and the API running, which is what the CI `e2e` job sets up. Browsers are not installed by `npm ci` — run `npx playwright install chromium webkit` once locally.

**Lighthouse budgets** — `frontend/lighthouserc.json`, run by the `lighthouse` CI job against Postgres and a live API, because a score measured on an empty catalogue means nothing. Three runs per URL asserted on the median; a single run on a shared CI box is too noisy to gate on. Gates performance ≥ 0.75, accessibility and SEO ≥ 0.9, LCP ≤ 4s, CLS ≤ 0.1 and total transfer ≤ 2.5MB. Tune the thresholds from the first real run.

### 5.4 CI/CD

`.github/workflows/ci.yml`:

1. `static` — format check, lint, typecheck, unit tests + coverage. No database, no browsers; fails in ~2 minutes.
2. `e2e` — matrix over `android-chrome` and `ios-safari`, with a Postgres service, `migrate deploy`, `db seed`, and only the one browser installed per job.
3. `docker` — builds the image with GHA layer cache. Wire registry push and deploy here.

`concurrency` cancels superseded runs.

## 6. Cross-platform: iOS vs Android

### 6.1 Differences that will bite

|                      | Android (Chrome)                    | iOS (Safari 17+)                                                                                              |
| -------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Install              | `beforeinstallprompt`, programmatic | No API. Share → Add to Home Screen, manually                                                                  |
| Manifest             | Fully honoured                      | Only `name`, `short_name`, `icons`, `display`, `start_url`; `apple-mobile-web-app-*` meta tags still required |
| Icon                 | Manifest icons, maskable supported  | `apple-touch-icon` only, no transparency, no maskable                                                         |
| Push                 | Web Push, works                     | Web Push only when **installed** to home screen, 16.4+; no prompt in the browser tab                          |
| Background sync      | `BackgroundSyncPlugin` works        | Unsupported — retry on next app open instead                                                                  |
| Storage eviction     | Quota-based, gradual                | Whole-origin eviction after ~7 days of no use (ITP)                                                           |
| Standalone detection | `display-mode: standalone`          | Also `navigator.standalone`                                                                                   |
| Safe areas           | Rarely needed                       | `viewport-fit=cover` + `env(safe-area-inset-*)` mandatory                                                     |

`InstallPrompt.tsx` implements both paths: stash `beforeinstallprompt` and replay it from a real user gesture (the event is valid once), or show Share-sheet instructions on iOS.

**The eviction rule is the one that matters commercially.** Do not treat the client cart as durable on iOS — it can vanish. That is why the cart also lives server-side.

### 6.2 App stores

- **Android:** a PWA can ship to Play as a Trusted Web Activity via Bubblewrap (`npx @bubblewrap/cli init --manifest https://…/manifest.webmanifest`). Requires Digital Asset Links at `/.well-known/assetlinks.json` and a signing key. Play also expects a privacy policy and a data-safety declaration.
- **iOS:** no App Store path for a PWA. A wrapper (Capacitor) is the only route, and Apple rejects thin web wrappers under guideline 4.2. Plan for home-screen install on iOS, Play listing on Android if you want store presence.
- Either way the web app is the product; a store listing is distribution, not architecture.

### 6.3 Storage and permissions

- **Cookies** for auth (httpOnly, `sameSite=lax`). Not `localStorage`.
- **Cache Storage** for assets and catalogue reads, with entry caps and `purgeOnQuotaError`.
- **localStorage** only for dismissible UI state (`bb:install-dismissed-at`). Never anything you would miss.
- **IndexedDB** holds offline order drafts (`frontend/src/lib/offline/orderQueue.ts`) — it survives better than localStorage and handles structured data. Each draft is keyed by `requestId`, which is what makes replay idempotent. Five failed attempts gives up, and a 4xx on replay drops the draft rather than retrying something that will never succeed.
- **The wishlist is server-side**, not localStorage, for the eviction reason above: a list curated over a month disappearing is worse than a lost cart. It is keyed by user or by the same anonymous cookie as the cart, and merged onto the account at sign-in.
- **Permissions:** request at the point of use, never on load. Geolocation only when the customer taps "use my location" for delivery; notifications only after a first successful order (iOS gives one prompt per install and a denial is effectively permanent). `Permissions-Policy` in `frontend/next.config.ts` denies camera and microphone outright.

## 7. Known gotchas, collected

1. `@serwist/next`'s webpack plugin is incompatible with Next 16's Turbopack default — use the CLI post-build step.
2. `serwist.config` must be `.mts`.
3. Central package management is not optional here: without `Directory.Packages.props` pinning `EntityFrameworkCore.Relational`, the Npgsql provider and the EF Design package resolve different assembly versions and the build fails with CS1705.
4. With central package management enabled, NuGet refuses to restore while extra machine-level feeds exist — hence `backend/nuget.config` clearing them.
5. `middleware.ts` is deprecated in Next 16 — the file is `proxy.ts` and the export is `proxy`.
6. Node's `Request` rejects relative URLs, so tests need an absolute `NEXT_PUBLIC_API_URL`.
7. jsdom has no fetch family and no WebCrypto; see the custom test environment.
8. `NEXT_PUBLIC_*` is build-time, not runtime.
9. Never cache `/sw.js` at the CDN.
10. EF Core migrations fail a `TreatWarningsAsErrors` build until `.editorconfig` exempts `**/Migrations/*.cs`.
11. `JsonIgnoreCondition.WhenWritingNull` silently turns `{ "user": null }` into `{}`, which the TypeScript client reads as `undefined`. The API writes nulls.
12. `upgrade-insecure-requests` in the CSP kills the service worker on a plain-http origin: the precache fetches are rewritten to https, fail with a TLS error, and the worker never installs. The app still renders, so this fails silently — `frontend/e2e/pwa.spec.ts` now asserts the directive is absent.
13. `npm audit` reports high-severity advisories in build-only transitive dependencies (`browserslist` via `@serwist/next`). The fix is a breaking downgrade; recheck when Serwist publishes a patched release rather than forcing `audit fix --force`.

## 8. What is deliberately not here yet

Automatic release of stock held by an abandoned online order; delivery pricing; review photos on durable storage rather than the container's disk, and EXIF stripped from them; distributed rate limiting in Redis (the in-memory limiter does not survive more than one instance); image CDN; error tracking; and analytics. Each has a placeholder in the schema, the tag types, or the compose file where it will attach.

Cart endpoints, merge-on-login, checkout, Hubtel payments, the admin surface, transactional email and password reset are all built — this section used to say otherwise. Email and payments ship switched off and turn on when their credentials are set.

`THINGS-TO-DO.md` at the repository root tracks all of it with current status.
